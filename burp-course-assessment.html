Stage 4 · Weeks 17–20

Assessment Prep: BSCP Certification Track

Everything in Stages 1–3 converges here. This stage maps your training onto the Burp Suite Certified Practitioner (BSCP) exam, then drills exam conditions with mock scenarios, timed challenges, and a final readiness gate before you book the real thing.

Verify before you register

PortSwigger periodically updates exact BSCP logistics (price, exact duration, retake policy, environment details). The structure described below reflects the exam's well-established practical format; confirm current specifics on the official pages linked in Module 1 before scheduling.

01BSCP Exam Blueprint

Format

A timed, fully practical exam (no multiple choice) against two realistic, deliberately vulnerable web applications hosted by PortSwigger. You're given Burp Suite Professional in the exam environment. Valid for five years once passed.

Goal

Find and chain vulnerabilities across each application to retrieve a specific piece of secret/confidential data — proof of exploitation, not just proof of a bug.

Skills tested

The full PortSwigger Web Security Academy topic list: injection, XSS, access control, authentication, CSRF/CORS, SSRF, request smuggling, JWT, deserialization, business logic, GraphQL/API, and more — almost always requiring you to chain 2+ classes together.

Grading

Pass/fail based on successfully extracting the target secret(s) within the time limit — partial credit for "found the bug but didn't complete the chain" is not how these practical formats typically work, so exploitation discipline matters as much as discovery.

03Mock Exam 1 — "NimbusCart" (2 hours, timed)

Scenario

NimbusCart is an e-commerce app. You have a standard customer account. Somewhere in the checkout/coupon flow and the account-settings API, two chained vulnerabilities together expose an admin's session. Your goal: retrieve the admin's session token or equivalent proof of takeover within 2 hours, working only in Burp.

Hint tier 1 (open only after 30 minutes stuck)
Start with the account-settings API — compare its authorization enforcement against the web UI's. One of the two surfaces checks ownership; the other doesn't.
Hint tier 2 (open only after 60 minutes stuck)
The coupon-application endpoint reflects a user-supplied field into an internal support-ticket system without sanitization — that's your second half of the chain once you have a foothold from the access-control gap.
Grading rubric
Full pass: identified both vulnerability classes, chained them, and produced working proof of admin-session access with saved Repeater evidence. Partial: found one of the two independently but didn't chain them — treat this as a "study the chaining mindset again" signal, not a pass.

04Mock Exam 2 — "Meridian API" (2 hours, timed)

Scenario

Meridian is an internal-tools API-only backend (JSON everywhere, GraphQL on /graphql) fronted by a JWT-based auth service. Your goal: escalate from a read-only API key to retrieving another tenant's confidential record via any valid chain.

Hint tier 1
Introspect the GraphQL schema first — there's a mutation exposed that the UI never calls, gated only by a role check performed client-side.
Hint tier 2
The JWT's kid header is used to look up a signing key from a path you can influence — combine that with the exposed mutation from hint 1.
Grading rubric
Full pass: working forged token demonstrating cross-tenant access, saved as evidence. Note your time-to-first-lead versus time-to-full-chain separately — BSCP rewards efficient triage as much as raw skill.

Why timed drills matter

BSCP's clock is the real constraint for most candidates, not knowledge gaps. Drilling under a visible countdown builds the triage instinct — recognizing in the first two minutes which vulnerability class you're likely looking at — that separates a pass from a near-miss.

06One-Page Revision Checklist

  • Every input point enumerated: GET/POST params, cookies, headers, JSON/XML body fields, file names
  • Two accounts created for every access-control/IDOR test
  • SQLi: error-based, boolean-blind, time-based, UNION all attempted before ruling an input clean
  • XSS: context identified before payload chosen; confirmed in Render tab, not just reflected
  • CSRF: token removed, emptied, reused, and Content-Type swapped
  • Session tokens run through Sequencer at least once per engagement
  • CORS: Origin reflection and null-origin both tested
  • SSRF: Collaborator used to confirm even when no visible response changes
  • JWT: alg:none, weak-secret, and confusion attacks all attempted
  • Rate limits tested on login, OTP, and password reset specifically
  • Every finding has a saved raw request/response before moving to the next test
  • Security headers audited even when not the main focus (cheap, complete findings)
  • Scope respected exactly — no testing outside documented boundaries, ever

Burp hotkeys
Ctrl+R Repeater · Ctrl+I Intruder · Ctrl+S Scanner · Ctrl+B Comparer · Ctrl+U URL-decode selection · Ctrl+Shift+U URL-encode · Ctrl+B (Decoder tab) Base64 decode
CIA triad
Confidentiality, Integrity, Availability — the three properties every vulnerability's impact ultimately maps back to.
CVSS base metric groups
Attack Vector, Attack Complexity, Privileges Required, User Interaction, Scope, plus Confidentiality/Integrity/Availability impact.
CWE vs OWASP
CWE (Common Weakness Enumeration) is a specific technical defect taxonomy (e.g. CWE-89 SQL Injection); OWASP Top 10 is a risk-category ranking — a single OWASP category can map to several CWEs.
Chaining, in one sentence
Combining two individually low/medium findings so the output of one becomes the input/prerequisite for the next, producing an impact greater than either alone.

08Full Interview Question Bank

Fundamentals

  1. Explain the request/response cycle and where a proxy like Burp sits in it.
  2. What's the difference between authentication and authorization, with an example bug for each?
  3. Why does HTTPS require Burp to install its own CA certificate to intercept traffic?
  4. Name three cookie attributes and what each protects against.

Burp tool usage

  1. When would you choose Pitchfork over Cluster bomb in Intruder?
  2. How does Sequencer decide a token is "weak"?
  3. What's the practical difference between Scanner's crawl-only and crawl-and-audit modes?
  4. How would you use Match and Replace to test how an app behaves without a specific security header?

Vulnerability-specific

  1. Walk me through confirming blind SQL injection without any visible error or content difference.
  2. What makes DOM-based XSS harder to find than reflected XSS with automated tools?
  3. Describe two ways to bypass a naive file-upload extension filter.
  4. How does algorithm confusion in JWT verification actually work?
  5. What's a real-world business-logic flaw you'd test for in a checkout flow?
  6. Explain CL.TE request smuggling in your own words.

Methodology & behavioral

  1. Tell me about a time you had to decide a finding was a false positive. How did you confirm it?
  2. How do you keep testing within scope when a vulnerability chain seems to lead just outside it?
  3. Describe how you'd communicate a Critical finding to a client mid-engagement, before the final report.
  4. What's your process for writing a remediation recommendation you're confident a developer can actually implement?

10Exam-Day Strategy

Time-boxDo this
First 15–20 minRecon both applications lightly before committing deeply to either — note every role, every API route, every parameter that looks unusual. Don't start exploiting yet.
Next 60–90 minWork the application that gave you the clearest early lead first — momentum matters more than "fairness" between the two targets.
Midpoint checkIf you have zero solid leads on one target by the halfway mark, deliberately switch targets rather than sunk-cost your way through it.
Final 30 minStop exploring, focus entirely on completing/chaining a lead you already have — a finished chain beats three half-finished ones.
ThroughoutKeep a running scratch note of every parameter/finding as you go — you will not remember it all under time pressure, and re-discovery costs minutes you don't have.

Read PortSwigger's own exam hints and guidance in the final week before your booking — it's written by the people who set the exam.

11After Certification

Keep current: work new PortSwigger Academy labs as they're published, read disclosed bug-bounty reports for the vulnerability classes you're weakest in, and keep a lab environment running so testing muscle memory doesn't atrophy. You can verify your certification once issued. If you want to keep climbing, adjacent certifications worth researching next include OSCP/OSWE (offensive security, broader exploitation) and CRTP (Windows/AD-focused) — evaluate based on whether your next goal is deeper web application work or broader infrastructure penetration testing.
