Stage 4 · Weeks 17–20

Assessment Prep: BSCP Certification Track

Everything in Stages 1–3 converges here. This stage maps your training onto the Burp Suite Certified Practitioner (BSCP) exam, then drills exam conditions using real PortSwigger Academy labs before you book the real thing.

Verify before you register

PortSwigger periodically updates exact BSCP logistics (price, exact duration, retake policy, environment details). The structure described below reflects the exam's well-established practical format; confirm current specifics on the official pages linked in Module 1 before scheduling.

01BSCP Exam Blueprint

Format

A timed, fully practical exam (no multiple choice) against two realistic, deliberately vulnerable web applications hosted by PortSwigger. You're given Burp Suite Professional in the exam environment. Valid for five years once passed.

Goal

Find and chain vulnerabilities across each application to retrieve a specific piece of secret/confidential data — proof of exploitation, not just proof of a bug.

Skills tested

The full PortSwigger Web Security Academy topic list: injection, XSS, access control, authentication, CSRF/CORS, SSRF, request smuggling, JWT, deserialization, business logic, GraphQL/API, and more — almost always requiring you to chain 2+ classes together.

Grading

Pass/fail based on successfully extracting the target secret(s) within the time limit — partial credit for "found the bug but didn't complete the chain" is not how these practical formats typically work, so exploitation discipline matters as much as discovery.

03Mock Exam 1 — Access Control + Authentication Chain (2 hours, timed)

This mirrors the BSCP format directly: two real vulnerability categories, chained, under a clock — using labs you select yourself so every run is fresh.

  1. Open Access control and Authentication on Web Security Academy.
  2. Pick one lab from each category that you have not already solved, at the highest difficulty available to you (Expert if you've cleared the Practitioner tier in that category, Practitioner otherwise).
  3. Set a 2-hour timer for both labs combined.
  4. Solve both without opening the built-in "Solution" tab until the timer ends — treat it exactly like exam conditions.
Stuck after 30 minutes? General triage, not a lab-specific hint
Re-read every response header and cookie you've been ignoring. Diff a low-privilege response against a high-privilege one in Comparer. Run Param Miner on the endpoint — labs at this difficulty often hide the deciding factor in an undocumented parameter or header rather than the obvious form field.
Grading rubric
Full pass: solved both labs within 2 hours without checking solutions. Partial: needed the built-in solution for one — treat that category as a gap and revisit its Stage 2 module before your next mock. Track your time-to-solve per lab; falling time across repeated mocks is the real signal you're exam-ready, more than any single pass/fail.

04Mock Exam 2 — API/GraphQL + JWT Chain (2 hours, timed)

Same format, aimed at the API-heavy side of the exam blueprint — this is the pairing most candidates under-practice relative to classic web-form vulnerabilities.

  1. Open GraphQL API vulnerabilities and JWT on Web Security Academy.
  2. Pick one unsolved lab from each, highest difficulty available to you.
  3. Set a 2-hour timer for both labs combined.
  4. Work them exactly as in Mock Exam 1 — no solution tab until time is up.
Stuck after 30 minutes? General triage, not a lab-specific hint
On GraphQL: always try an introspection query first, even if the docs say it's disabled — partial introspection is common. On JWT: check every header field (alg, kid, jku), not just the payload claims; the forging technique is usually signalled by an unusual header value.
Grading rubric
Full pass: working exploit chain demonstrating the intended impact (data exposure, privilege escalation, or account takeover depending on the lab), solved within time. Note your time-to-first-lead versus time-to-full-chain separately — BSCP rewards efficient triage as much as raw skill.

  • Two accounts created for every access-control/IDOR test
  • SQLi: error-based, boolean-blind, time-based, UNION all attempted before ruling an input clean
  • XSS: context identified before payload chosen; confirmed in Render tab, not just reflected
  • CSRF: token removed, emptied, reused, and Content-Type swapped
  • Session tokens run through Sequencer at least once per engagement
  • CORS: Origin reflection and null-origin both tested
  • SSRF: Collaborator used to confirm even when no visible response changes
  • JWT: alg:none, weak-secret, and confusion attacks all attempted
  • Rate limits tested on login, OTP, and password reset specifically
  • Every finding has a saved raw request/response before moving to the next test
  • Security headers audited even when not the main focus (cheap, complete findings)
  • Scope respected exactly — no testing outside documented boundaries, ever

08Full Interview Question Bank

Every question below expands into a model answer with a concrete example. Try answering out loud first, then open it — that's the closest you'll get to real interview pressure without another person in the room.

Fundamentals

1. Explain the request/response cycle and where a proxy like Burp sits in it.

A browser sends a request line (method + path + version), headers, and optionally a body; the server replies with a status line, response headers, and a body. Burp sits as a man-in-the-middle between the two: it terminates the client's connection, forwards a request of its own to the real server, and does the same in reverse for the response — so every byte in both directions passes through it and can be read or edited.

GET /account HTTP/1.1
Host: example.com
Cookie: session=abc123

-- Burp sits here, holding the request before it ever reaches example.com --

HTTP/1.1 200 OK
Content-Type: application/json
{"user":"alice"}
2. What's the difference between authentication and authorization, with an example bug for each?

Authentication answers "who are you" — login, MFA, session issuance. Authorization answers "what are you allowed to do" and is checked on every subsequent request. An AuthN bug breaks the identity check itself; an AuthZ bug lets a correctly-identified user reach data or actions they shouldn't.

AuthN example: a 2FA flow that trusts a client-supplied flag — intercept the verification response and flip {"2fa_required":true} to false to skip the second factor entirely.
AuthZ example: GET /api/orders/1001 returns your order; changing it to /api/orders/1002 while still using your own session returns someone else's — a classic IDOR.

3. Why does HTTPS require Burp to install its own CA certificate to intercept traffic?

TLS is designed so only the real server can produce a certificate the browser trusts for that domain. When Burp intercepts HTTPS, it generates its own certificate for each host on the fly and signs it with Burp's own Certificate Authority. The browser will only accept that certificate silently if it already trusts Burp's CA — which is exactly what installing cacert.der does. Skip that step and every HTTPS site throws NET::ERR_CERT_AUTHORITY_INVALID or similar, because the browser correctly detects a man-in-the-middle it wasn't told to trust.

4. Name three cookie attributes and what each protects against.

HttpOnly blocks JavaScript from reading the cookie via document.cookie, so a successful XSS can't trivially exfiltrate the session token. Secure stops the cookie being sent over a plain HTTP connection, closing off network-level interception. SameSite=Strict (or Lax) stops the cookie being attached to cross-site requests, which is the main defense against CSRF. Example: Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax — missing any one of these three narrows the attack surface Burp should specifically go looking for.

Burp tool usage

5. When would you choose Pitchfork over Cluster bomb in Intruder?

Pitchfork walks multiple payload lists in lockstep — position 1 gets item 1 from list A and item 1 from list B on the same request, then both move to item 2 together. Use it when the values are already correlated, like a leaked list of matched username:password pairs from a breach dump. Cluster bomb instead tries every combination of every list — appropriate for generic credential stuffing where usernames and passwords aren't paired, but it explodes combinatorially (100 usernames × 100 passwords = 10,000 requests), so reach for Pitchfork whenever the pairing is already known.

6. How does Sequencer decide a token is "weak"?

Sequencer captures thousands of live samples of a token, then runs statistical randomness tests (based on FIPS-style bit-level analysis) against the character positions to estimate how many bits of genuine unpredictability the token actually contains — its "effective entropy." A token that looks long but is built from a timestamp plus a short counter might report well under 64 effective bits even though it's 32 characters long. Anything meaningfully below 64 bits of effective entropy is reportable as a predictable/weak session or CSRF token (CWE-330), because it starts to become feasible to guess or narrow down valid values.

7. What's the practical difference between Scanner's crawl-only and crawl-and-audit modes?

Crawl-only just walks the application's links and forms to build the site map — no payloads are sent, so it's safe to run early and fast even against a large app. Crawl-and-audit does that same walk but also fires the full active payload set at every parameter it finds along the way, which is slower and generates real attack traffic. In practice: run crawl-only first for a quick attack-surface map you can review, then run crawl-and-audit (or audit-only against selected items) once you've confirmed scope and login handling are configured correctly.

8. How would you use Match and Replace to test how an app behaves without a specific security header?

Add a response-side Match and Replace rule that matches the header and replaces it with nothing, then browse normally — the app never sees the header leave the proxy, letting you observe real behavior without touching server config.

# Proxy -> Options -> Match and Replace
Type: Response header   Match: X-Frame-Options.*   Replace: (empty)
# Now load the page in an iframe on a test page you control to confirm clickjacking exposure

Vulnerability-specific

9. Walk through confirming blind SQL injection without any visible error or content difference.

When the response looks identical whether the injected condition is true or false, fall back to a side channel the app can't hide: time or an out-of-band callback. Send a baseline request, then a delayed one, and compare response times across several trials to rule out network noise before concluding.

username=admin' AND SLEEP(0)--     # baseline, should return immediately
username=admin' AND SLEEP(5)--     # if the response now takes ~5s longer, the query executed your injected SQL

# Fully blind / no timing signal available -> out-of-band via Collaborator
username=admin' AND (SELECT 1 FROM (SELECT SLEEP(5))a) UNION SELECT null-- # or an OOB DNS lookup payload
10. What makes DOM-based XSS harder to find than reflected XSS with automated tools?

Reflected XSS round-trips through the server — the payload appears in the request and again in the raw HTML response, which a scanner or passive proxy can pattern-match directly. DOM-based XSS never touches the server at all: client-side JavaScript reads an attacker-controlled source like location.hash or document.referrer and writes it straight into a dangerous sink like innerHTML or eval(). Since the vulnerable data flow lives entirely inside compiled/minified JavaScript running in the browser, you need to actually read the client-side code or use a dynamic tool like Burp's DOM Invader to trace source-to-sink flows — a purely server-side or regex-based scanner has nothing to look at.

11. Describe two ways to bypass a naive file-upload extension filter.

Double extension: upload shell.php.jpg — a filter that only checks the string ends in an allowed image extension misses that the server may still execute anything containing .php anywhere in the name, depending on the web server's handler configuration. Case variation: upload shell.pHp — a blocklist regex written as /\.php$/ (case-sensitive) won't catch it, while the OS/webserver's extension handling is typically case-insensitive on Windows and sometimes on Linux depending on config. Other angles worth knowing: alternate executable extensions the filter's list forgot (.phtml, .php5), and spoofing the Content-Type multipart header to image/jpeg when the check only inspects that header rather than the file's actual bytes.

12. How does algorithm confusion in JWT verification actually work?

Some JWT libraries expose one generic verify(token, key) function that behaves differently depending on the alg claimed in the token's own header: for RS256 it treats key as an RSA public key, but for HS256 it treats the same key value as a raw HMAC secret. If the server is configured to trust RS256 tokens using a public key that's actually knowable to an attacker (RSA public keys are, by design, not secret), the attacker can craft a brand-new token, set its header to "alg":"HS256", and sign it using that public key as the HMAC secret. If the server's verification code doesn't pin the expected algorithm and just does whatever the token's own header says, it will incorrectly validate the forged signature — letting the attacker set arbitrary claims like "role":"admin".

13. What's a real-world business-logic flaw you'd test for in a checkout flow?

A single-use discount coupon that isn't actually enforced atomically: fire several "apply coupon" requests at the exact same moment with Burp's "send group in parallel" feature, and if the backend checks "has this code been used" and marks it used as two separate, non-atomic steps, multiple concurrent requests can all read "not yet used" before any of them commits — applying the discount multiple times on one order. Other checkout-specific angles worth testing: negative item quantities crediting the account instead of charging it, and whether the final price is recalculated server-side or blindly trusted from a client-supplied total field.

14. Explain CL.TE request smuggling in your own words.

The front-end (load balancer/CDN) and the back-end application server disagree about how to determine where one HTTP request ends. CL.TE means the front-end trusts the Content-Length header to find the body's end, while the back-end trusts Transfer-Encoding: chunked instead. An attacker crafts a request with both headers present but contradictory: the front-end reads only up through the length it expects and forwards the connection onward, but the back-end — parsing by chunked encoding — treats part of what the front-end considered "the next request" as a lingering, smuggled tail of the previous one. That tail then gets prepended to whatever real request the next unlucky user sends over the same reused connection, letting the attacker inject a request that appears to come from someone else.

POST / HTTP/1.1
Host: target.com
Content-Length: 13
Transfer-Encoding: chunked

0

Methodology & behavioral

15. Tell me about a time you had to decide a finding was a false positive. How did you confirm it?

Frame the answer around process, since interviewers are testing rigor, not the specific bug: Scanner flags something → don't take the label at face value → reproduce the exact request manually in Repeater → check whether the "vulnerable" behavior actually occurs (e.g. does the injected script tag genuinely appear unescaped in the Render tab, or was it HTML-entity-encoded and Scanner just matched the raw string in the response body) → only mark it a real finding once you've watched the impact happen with your own eyes, not inferred it from a signature match. Example: Scanner reports reflected XSS because it found your payload string in the response — but on inspection the app had encoded < to &lt;, so nothing executes; that's a false positive worth closing immediately so it doesn't dilute the report's credibility.

16. How do you keep testing within scope when a vulnerability chain seems to lead just outside it?

Stop at the boundary the moment you recognize it, document exactly what you observed and why you believe the chain continues (e.g. "this SSRF appears able to reach an internal host that isn't in our authorized IP range"), and raise it to the client immediately rather than proceeding — either to get written authorization to extend scope for that specific path, or to note it in the report as an observation for them to investigate internally. Testing past an agreed boundary, even when technically trivial, is the fastest way to turn a legitimate engagement into a legal problem.

17. Describe how you'd communicate a Critical finding to a client mid-engagement, before the final report.

Follow whatever emergency-contact process was defined in the rules of engagement — usually an immediate phone call or a designated secure channel, not email with exploit details attached in plaintext. Give them enough to act now (affected system, rough nature of the issue, whether it appears to be actively exploited by anyone else) without necessarily handing over a working exploit over an insecure channel. Follow up with a short written summary once the verbal notification is done, and continue the full technical write-up for the final report — the goal of the interim notice is speed, not completeness.

18. What's your process for writing a remediation recommendation you're confident a developer can actually implement?

Target the root cause, not the symptom, and be specific enough that a developer doesn't have to guess what "sanitize the input" means in practice. Reference the exact mechanism (parameterized queries, not "escape quotes"), and where useful, show the concrete fix pattern rather than describing it abstractly.

-- Vague, unhelpful: "validate user input before using it in the query"

-- Specific and actionable:
-- Replace string-concatenated SQL with a parameterized query, e.g. (Python/psycopg2):
cursor.execute("SELECT * FROM users WHERE username = %s", (username,))
-- not: cursor.execute("SELECT * FROM users WHERE username = '" + username + "'")

11After Certification

Keep current: work new PortSwigger Academy labs as they're published, read disclosed bug-bounty reports for the vulnerability classes you're weakest in, and keep a lab environment running so testing muscle memory doesn't atrophy.
