Stage 3 · Weeks 11–16

Exploitation & Professional Methodology

This is where labs stop being single-vulnerability exercises and start requiring you to chain two or three findings together — exactly what BSCP and real assessments demand. The second half of this stage shifts from finding bugs to proving, scoring, and writing them up like a professional.

01Server-Side Request Forgery (SSRF)

CWE-918 · OWASP A10. The server itself fetches an attacker-supplied URL, letting you reach internal-only systems through it.

# Find parameters that accept URLs
url=, webhook=, callback=, fetch=, load=, import=

# Confirm with Burp Collaborator (out-of-band, works even fully blind)
url=https://YOUR-COLLABORATOR-SUBDOMAIN.oastify.com
# A DNS/HTTP hit in Collaborator = confirmed SSRF

# Internal network / cloud metadata probing (only after confirming SSRF)
url=http://127.0.0.1
url=http://169.254.169.254/latest/meta-data/                      # AWS
url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
url=http://metadata.google.internal/computeMetadata/v1/           # GCP

# Filter/WAF bypass — IP obfuscation
http://127.0.0.1 -> http://2130706433 (decimal) -> http://0x7f000001 (hex) -> http://127.1 -> http://0177.0.0.1 (octal)

# Open redirect chained into SSRF
url=https://trusted.com/redirect?url=http://127.0.0.1

Remediation: allow-list destination hosts server-side (never rely on blocklists/regex on the URL string), disable unused URL schemes, isolate the fetching service from internal networks/metadata endpoints.

02File Upload Vulnerabilities

PortSwigger topic

Bypass techniqueHow it works
Extension bypassshell.php.jpg, shell.pHp, shell.php%00.jpg, double extensions the server's regex misses
Content-Type bypassChange the Content-Type multipart header to image/jpeg while the body stays a script
Magic byte bypassPrefix the payload with a valid image header (e.g. GIF89a) so signature checks pass while the rest still executes server-side
Polyglot filesA single file that's simultaneously valid as an image and as executable code, depending on which parser reads it
Path traversal via filenameUpload as ../../var/www/html/shell.php if the filename isn't sanitized before use in a path

Chain: upload succeeds → confirm the file is stored somewhere web-accessible → confirm it executes as server-side code rather than being served statically → that's remote code execution, not just an upload flaw. Burp's Upload Scanner extension automates most of this matrix.

05JWT Attacks

PortSwigger topic

AttackMechanism
alg: noneSome libraries accept an unsigned token if the header claims no algorithm — strip the signature and set "alg":"none"
Weak secret brute forceHS256 tokens signed with a guessable secret can be cracked offline (hashcat) and re-signed with attacker-chosen claims
Algorithm confusion (RS256 → HS256)If the server accepts either algorithm and uses the same key material, sign a forged HS256 token using the RSA public key as the HMAC secret

Use the JSON Web Tokens Burp extension to decode, edit claims, and re-sign inline in Repeater — install it once in Stage 2's extension setup.

06API Security & GraphQL

See PortSwigger's API testing and GraphQL API vulnerabilities topics.

IssueTest
GraphQL introspection left enabledSend {__schema{types{name,fields{name}}}} — a full schema dump maps the entire API surface, including unused/admin fields
Batching abuseGraphQL/REST batch endpoints can bypass per-request rate limiting by packing many operations into one HTTP call
Mass assignmentAdd fields the client shouldn't set ("role":"admin", "isVerified":true) to a JSON body and see if the server blindly binds them to the model
Excessive data exposureAn endpoint returns a full internal object (password hash, internal flags) and relies on the client UI to hide fields — inspect the raw response, not the rendered page

Related, worth a pass in the same testing session: NoSQL injection on document-database-backed APIs, and prototype pollution in JavaScript-heavy backends.

07Business Logic Flaws & Race Conditions

Business logic vulnerabilities · Race conditions. The code does exactly what it says — the specification itself is wrong. No generic payload finds these; they require understanding the workflow.

PatternExample
Race conditionRedeem a single-use discount code or apply-once coupon multiple times by firing near-simultaneous requests — use Burp's built-in "Send group in parallel" (single-packet attack) or Turbo Intruder for precise timing
Workflow bypassSkip a required verification step by calling a later endpoint directly
Negative/decimal abuseNegative item quantity credits the account instead of charging it; sub-cent rounding repeated thousands of times
Trust boundary violationClient-side price/total sent to the server and trusted without server-side recalculation

08HTTP Request Smuggling & Host Header Attacks

HTTP request smuggling · HTTP Host header attacks · Web cache poisoning · Web cache deception. Front-end and back-end servers disagree on where one request ends and the next begins (conflicting Content-Length and Transfer-Encoding headers — CL.TE / TE.CL), letting an attacker smuggle a hidden second request. Burp's HTTP/1↔HTTP/2 toggle in Repeater plus the HTTP Request Smuggler extension automate desync detection. Related: manipulating the Host header to poison password-reset links or a cache when an app trusts it unvalidated.

10WAF & Filter Evasion — Consolidated Toolkit

Case mixing (ScRiPt), encoding layers (URL, double-URL, HTML entity, Unicode), comment injection inside keywords (UN/**/ION SEL/**/ECT), alternate syntax the filter's regex doesn't anticipate, and simply testing every parameter/header individually since WAFs are frequently misconfigured to only cover some routes.

11Insecure Deserialization & SSTI (introductory)

Insecure deserialization (CWE-502): untrusted serialized data (PHP objects, Java, Python pickle) is deserialized without validation — can lead to remote code execution via "gadget chains." Server-Side Template Injection: user input is rendered by a template engine (Jinja2, Twig, FreeMarker) instead of being treated as data — test with {{7*7}}-style markers per engine; a returned 49 confirms execution context. See also WebSockets and Web LLM attacks for emerging surfaces worth a pass on modern targets.

12Professional Pentest Methodology

Full lifecycle

  1. Scoping & rules of engagement — written authorization, in/out-of-scope assets, testing window, emergency stop contact.
  2. Reconnaissance & attack-surface mapping — passive review, authenticated crawl (Scanner), Param Miner for hidden parameters, manual click-through of every role.
  3. Vulnerability analysis — OWASP-Top-10-driven hypothesis testing per endpoint, not random payload spraying.
  4. Exploitation & chaining — combine findings (e.g., IDOR + weak JWT secret = full account takeover) to demonstrate real business impact.
  5. Evidence collection — save the raw request/response for every finding as you find it, with a timestamp; never reconstruct evidence from memory afterward.
  6. Risk rating — CVSS v3.1 base score plus a plain-language likelihood × impact call.
  7. Reporting — the finding template in Module 13, written for a technical fixer and an executive reader both.
  8. Retesting — confirm the specific fix closes the specific hole, and probe for regressions/bypasses of the patch itself.

CVSS v3.1 walkthrough (worked example)

Take an unauthenticated IDOR exposing other users' PII via a predictable numeric ID: Attack Vector: Network, Attack Complexity: Low, Privileges Required: None, User Interaction: None, Scope: Unchanged, Confidentiality: High, Integrity: None, Availability: None → base score 7.5 (High). Walking the vector string this way for every finding keeps severity ratings defensible and consistent across a report.

13Sample High-Quality Findings

High

Broken Object-Level Authorization on Order Retrieval Endpoint

CWE / OWASP
CWE-639 · OWASP A01:2021 – Broken Access Control
Affected endpoint
GET /api/v2/orders/{order_id}
Prerequisites
Any two authenticated customer accounts
Reproduction
1) Log in as User A, place an order, note the returned order_id (e.g. 10432). 2) Log in as User B; send GET /api/v2/orders/10432 with User B's session cookie in Repeater. 3) Observe HTTP 200 with User A's full order — items, shipping address, last-4 of payment card.
Evidence
Raw request/response pair captured in Burp Repeater (attach finding-01-request.txt / finding-01-response.txt); screenshot of rendered PII in the Render tab.
Business impact
Any authenticated customer can enumerate and read every other customer's order history and partial payment data — a systemic PII exposure affecting the full customer base, not a single account.
Remediation
Enforce a server-side ownership check (order.user_id == session.user_id) on every object-fetch before returning data; return 403/404 uniformly for both "not yours" and "doesn't exist" to avoid existence-leak as a secondary issue.
Retest criteria
Repeat reproduction steps with two accounts post-fix; confirm 403/404 returned and no order data present in the body for a non-owned order_id, across at least 5 sampled IDs.
Critical

Unauthenticated SQL Injection in Product Search (UNION-based)

CWE / OWASP
CWE-89 · OWASP A03:2021 – Injection
Affected endpoint
GET /search?q=
Prerequisites
None — endpoint is publicly reachable pre-authentication
Reproduction
1) GET /search?q=test' returns a 500 with a MySQL syntax error in the body. 2) GET /search?q=test' ORDER BY 5-- succeeds; ORDER BY 6-- errors, confirming 5 columns. 3) GET /search?q=test' UNION SELECT username,password,3,4,5 FROM users-- returns the full users table rendered into the search-results grid.
Evidence
Response body showing extracted username/password-hash pairs (redacted in the report body, full evidence in a restricted appendix).
Business impact
Complete compromise of the user database, including credential hashes, without any authentication — enables full account takeover at scale and is a reportable data-breach trigger in most jurisdictions.
Remediation
Replace string-concatenated SQL with parameterized queries/prepared statements; apply least-privilege to the search endpoint's DB account (no access to the users table at all); add a WAF rule as a compensating control while the code fix ships.
Retest criteria
Re-run the full detection payload set (error-based, boolean, UNION, time-based) against the endpoint; confirm no behavioral difference between true/false injected conditions and no error leakage.
High

Server-Side Request Forgery via Webhook URL Configuration

CWE / OWASP
CWE-918 · OWASP A10:2021 – SSRF
Affected endpoint
POST /api/integrations/webhook (url parameter)
Prerequisites
Authenticated account with integration-settings access (standard user role, not admin)
Reproduction
1) Set url to a Burp Collaborator subdomain; save; trigger the webhook test button. 2) Collaborator receives an HTTP interaction, confirming the server fetches attacker-controlled URLs. 3) Set url=http://169.254.169.254/latest/meta-data/iam/security-credentials/; the webhook "delivery log" in the UI reflects the response body, exposing temporary IAM credentials.
Evidence
Collaborator interaction log (DNS + HTTP); screenshot of leaked IAM credential JSON in the delivery-log UI.
Business impact
Any standard user can pivot from the application into the cloud provider's internal metadata service, potentially escalating to control of the underlying cloud account — impact well beyond the web application itself.
Remediation
Allow-list permitted destination hosts server-side; block requests to link-local/metadata ranges (169.254.0.0/16) and RFC1918 space at the network layer, not just in application code; disable metadata-service credential exposure via IMDSv2 (require a session token) at the cloud-provider level.
Retest criteria
Confirm the webhook feature rejects/errors on metadata and internal-range URLs; confirm Collaborator interactions no longer occur for out-of-allowlist hosts.

17Flashcards (Set 3) & Interview Questions (Batch 2)

SSRF vs. Open Redirect
Open redirect sends the victim's browser to a new URL; SSRF makes the server itself issue the request — far higher impact since it runs from inside the network.
CL.TE smuggling
Front-end uses Content-Length, back-end uses Transfer-Encoding (or vice versa for TE.CL) to decide where a request ends — the mismatch lets an attacker smuggle a hidden second request past the front-end's inspection.
JWT alg confusion
Forging an HS256 token using an RSA public key as the HMAC secret, when a server configured for RS256 verification will also accept HS256 tokens.
Why business logic bugs evade scanners
The request/response is syntactically and semantically "valid" by every technical measure — the flaw is only visible against the intended business rule, which no generic payload encodes.
CVSS Attack Vector: Network vs Adjacent vs Local
Network = exploitable remotely over the internet; Adjacent = requires same physical/logical network segment; Local = requires local access to the host — directly affects the base score.

Interview Questions — Batch 2

  1. Describe a vulnerability chain you'd build from a low-severity IDOR and a weak JWT signing secret.
  2. How do you distinguish a true SSRF from an app that just happens to make outbound requests as part of normal function?
  3. What makes race-condition testing different from every other vulnerability class in terms of tooling and timing?
  4. Walk through how you'd assign a CVSS score to a stored XSS that only fires in an internal admin panel.
  5. What's your process when a WAF is clearly blocking your payloads but you believe the underlying code is vulnerable?
  6. How would you explain the business impact of an HTTP request-smuggling finding to a non-technical stakeholder?
  7. What's the difference between reporting a finding as "Critical" versus "High," in your own words, independent of a CVSS calculator?
  8. Describe your evidence-collection discipline during a live engagement — what do you save, and when?
