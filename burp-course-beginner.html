Stage 1 · Weeks 1–4

Foundations & First Intercept

Before you touch Burp Suite you need to understand what it's actually watching. This stage builds the HTTP, session, and OWASP foundations, then gets Burp installed and doing real work: intercepting, replaying, and fuzzing your first requests.

Scope of practice

Everything in this course is built for authorized targets only: your own local labs, PortSwigger Web Security Academy, deliberately vulnerable apps (DVWA, OWASP Juice Shop, WebGoat) run on your machine, or engagements you hold written authorization for. Testing systems you don't own or lack permission to test is illegal under the CFAA (US) and equivalent computer-misuse laws elsewhere. Nothing here should be pointed at a live third-party site without a signed scope agreement.

01How the Web Actually Works

Why it matters · What it is · How Burp fits in

Why it matters: every vulnerability in this course — SQL injection, XSS, broken access control, all of it — is a mistake made somewhere inside an HTTP request or response. If you can't read one fluently, you can't find or explain any of them. What it is: Burp Suite is a proxy — it sits between your browser and every server you talk to, so before any of it makes sense, you need to be fluent in the thing it's showing you: an HTTP request and its response.

The request/response cycle

# Your browser sends a request...
GET /account/settings HTTP/1.1

Accept: text/html,application/xhtml+xml

# ...and the server answers
HTTP/1.1 200 OK

Server: nginx/1.25.4
Content-Type: text/html; charset=UTF-8
Set-Cookie: session=eyJhbGciOiJIUzI1NiJ9.abc123; HttpOnly; Secure; SameSite=Lax

Request lineMethod (GET/POST/PUT/DELETE/PATCH), path, HTTP version — the verb tells you the intended action; the path is your attack surface map.

HTTPS in one breath

TLS wraps the same HTTP conversation in encryption negotiated via a handshake (ClientHello → ServerHello → certificate → key exchange → encrypted traffic). Burp decrypts this by sitting as a man-in-the-middle your browser is told to trust — which is exactly why Module 8 has you install Burp's own CA certificate.

02Cookies, Sessions, Authentication & Authorization

Cookies & sessions

Most apps are stateless at the protocol level, so they fake memory using a session identifier stored in a cookie and mapped server-side to that user's data.

Cookie attributeWhat it doesMissing it means…
HttpOnlyBlocks JavaScript from reading the cookieAn XSS finding can steal the session outright
SecureOnly sent over HTTPSCookie can leak over any accidental HTTP request
SameSite=Strict/Lax/NoneControls cross-site sendingNone (or missing, on old browsers) widens CSRF exposure
Expires/Max-AgeSession lifetimeNo expiry = sessions live forever if stolen

Authentication vs. Authorization — the distinction the whole course rests on

Authentication (AuthN)

"Who are you?" — logging in, MFA, password reset, session issuance. Breaks in this layer are Auth Bypass findings (Stage 2, Module 6).

Authorization (AuthZ)

"What are you allowed to do?" — enforced after authentication, per object and per function. Breaks here are IDOR/BOLA and Broken Access Control (Stage 2, Modules 5 & 7).

Why this matters

A huge share of real-world (and BSCP exam) findings come from an app that authenticates you correctly, then forgets to check authorization on the very next request. You will test this distinction constantly.

Stateless auth preview: tokens & JWT

Modern APIs increasingly replace server-side sessions with a signed token the client holds and presents on every request (Authorization: Bearer <token>). JSON Web Tokens (JWT) are the dominant format — you'll attack their signature and claims logic in depth in Stage 3.

06Threat Modeling & Secure Testing Methodology

Every professional assessment — and the BSCP exam itself — follows roughly this loop. Memorize it now; every later module is a zoom-in on one step.

  1. Scope & rules of engagement — what's in/out of scope, testing windows, emergency contacts, written authorization.
  2. Reconnaissance — passive first (read the app, note tech stack, map roles), then active crawling.
  3. Attack surface mapping — every endpoint, parameter, header, and role combination becomes a row in your test matrix.
  4. Vulnerability analysis — hypothesize per OWASP category, test methodically rather than randomly.
  5. Exploitation & validation — prove impact safely (read-only proof of access beats destructive proof every time).
  6. Evidence collection — save the raw request/response for every finding as you go, not at the end from memory.
  7. Reporting — severity, reproduction steps, business impact, remediation (full template in Stage 3 · M13).
  8. Retesting — confirm the fix actually closes the hole, not just that the specific payload now fails.
Legal & ethical baseline

Written authorization before any test. Respect scope boundaries exactly as documented. Prefer non-destructive proof of impact (read one record, don't drop a table). Stop and report immediately if you find evidence of a prior, unrelated breach. Never retain client data beyond what the engagement requires.

08Browser Proxy Configuration & CA Certificate

Firefox — manual configuration

  1. Firefox → Settings → Network Settings → Manual proxy configuration.
  2. HTTP Proxy: 127.0.0.1, Port: 8080. Check "Also use this proxy for HTTPS".
  3. Or install the FoxyProxy Standard extension, add a profile (Burp | 127.0.0.1 | 8080), and toggle it with one click instead of digging through settings each time.

Installing Burp's CA certificate (required for HTTPS interception)

  1. With the proxy active, browse to http://burpsuite (or http://127.0.0.1:8080) to reach Burp's welcome page.
  2. Click CA Certificate to download cacert.der.
  3. Firefox → Settings → Privacy & Security → View Certificates → Import → select cacert.der → check "Trust this CA to identify websites".
  4. Chrome/Edge (Windows): import via chrome://settings/certificates → Authorities → Import. macOS system-wide: add to Keychain Access and set to "Always Trust". Linux: depends on distro's CA store (e.g. update-ca-certificates after copying to /usr/local/share/ca-certificates/).
  5. Test: browse to any HTTPS site with Intercept OFF — it should load cleanly and appear in Proxy → HTTP History with no certificate warnings.

09Proxy & Intercept

Why it matters: it's your primary audit trail and the entry point into every other Burp tool — nothing else in this course works until you can see and hold a request.
What it is: the core MITM engine — every request/response you and your browser exchange with the target flows through it and can be paused, read, and edited.
When to use it: Intercept ON only when you need to modify a specific request live; leave it OFF and read HTTP History for normal browsing — flipping this habit is the single biggest quality-of-life improvement for new users.

  1. Proxy → Intercept → turn Intercept on.
  2. Browse to your target — the request pauses in the Intercept tab.
  3. Read and edit headers, cookies, body — change values, add headers, alter the body.
  4. Forward to send it on (modified or not); Drop to discard it and simulate a connection failure.
  5. Everything — forwarded, dropped, intercepted or not — lands in Proxy → HTTP History. Right-click any entry to send it to Repeater, Intruder, or Scanner.

Match & Replace — automating repetitive edits

# Proxy → Options → Match and Replace
Type: Request header   Match: User-Agent.*        Replace: User-Agent: Mozilla/5.0 Googlebot/2.1
Type: Request URL      Match: ^http://            Replace: https://
Type: Request header   Match: (nothing)           Replace: X-Custom-Header: testing   # adds to every request
Type: Response header  Match: X-Frame-Options.*   Replace: (empty)                    # strips a header for testing

10Repeater — Manual Request Replay

Repeater is where you'll spend most of your manual-testing hours: capture once, then tweak and resend the same request as many times as it takes to confirm a hypothesis.

FeatureUse
Request pane (left)Edit the raw request before sending
Response pane (right)Full response — Pretty / Raw / Hex, plus a Render view (mini-browser) that's invaluable for confirming XSS actually executes
◀ / ▶ history arrowsStep back through every variation you've tried in this tab
Target fieldChange host/port without hand-editing the Host header
HTTP/1 ↔ HTTP/2 toggleRelevant later for request-smuggling work

Worked example: probing a login form

POST /login HTTP/1.1
Host: target.local
Content-Type: application/x-www-form-urlencoded

username=admin&password=anything

# Send, read the response, change ONE variable, send again:
username=admin'--&password=anything     # does the error change?
username=notauser&password=anything     # does the error wording differ (username enumeration)?

This "change one thing, observe, repeat" discipline is the whole job — Intruder later automates exactly this loop at scale.

12Decoder & Comparer

Decoder

Encode/decode Base64, URL, HTML entities, hex, ASCII hex, octal, binary, and gzip — chainable, so you can peel back multiple layers of obfuscation. Use "Smart decode" when you don't know the encoding.

Example: an ID param dXNlcjEyMw== → Base64-decode → user123 → edit → re-encode → paste back into Repeater.

Comparer

Diffs two requests or responses word-by-word or byte-by-byte. Send two responses to Comparer to spot exactly what changed between a valid and invalid login, or before/after a payload.

Classic use: comparing two session tokens, or two Intruder responses of near-identical length to find the one meaningful difference.

15Knowledge Check

Why does Burp need its own CA certificate installed in the browser?
Because Burp performs a man-in-the-middle: it terminates the browser's TLS connection and opens its own to the server. Without the browser trusting Burp's CA, every HTTPS site would show a certificate warning since Burp's certificate wasn't issued by a browser-trusted authority.
What's the practical difference between Authentication and Authorization, and why does it matter for testing?
Authentication proves identity ("who are you"); Authorization decides permissions ("what can you do"). Apps frequently authenticate correctly but fail to re-check authorization on every subsequent request/object — that gap is where IDOR and broken access control live, so the two must always be tested separately.
You send a request with Sniper vs. Battering ram in Intruder — same payload list, same two marked positions. What's different about the requests each produces?
Sniper puts the payload into one position at a time (all other marked positions stay at their original value) — good for isolating which single parameter matters. Battering ram inserts the same payload into every marked position on every request simultaneously — useful when two fields must match, like testing the same injection string in both a username and a password field at once.
A 404 response turns into a 403 once you're logged in as a low-privileged user, for a URL you guessed. What does that suggest?
The object likely exists but access is denied once the app can identify you — a classic access-control probe point. It can also be an information-disclosure issue on its own (confirming an object's existence to unauthorized users) worth noting for Stage 2's access-control module.

16Flashcards — Set 1

HttpOnly cookie flag
Blocks JavaScript (document.cookie) from reading the cookie — mitigates session theft via XSS.
SameSite=Strict
Cookie is never sent on cross-site requests, including top-level navigation — strongest CSRF mitigation, but can break legitimate cross-site flows.
Man-in-the-middle proxy
A tool (Burp) positioned between client and server that terminates and re-establishes the connection so traffic can be read/modified in transit.
Same-Origin Policy
Browser rule: scripts can only read responses from the same scheme+host+port they were loaded from, unless explicitly relaxed (CORS).
Idempotent HTTP method
Repeating the same request produces the same server state (GET, PUT, DELETE) — POST is not idempotent by convention.
Sniper vs. Cluster bomb
Sniper = one payload set, one position at a time. Cluster bomb = multiple payload sets, every combination tried.
Why Intercept OFF is the default habit
HTTP History captures everything passively; Intercept ON is reserved for the moment you need to edit one specific request live.
401 vs 403
401 = not authenticated (who are you?). 403 = authenticated but not authorized (I know who you are, you can't do this).
